# 图表分配优化

## 使用场景与设计初衷

多窗口看盘在持续更新和移动光标时会重复读取完整 SDK 系列。末点读取及二分查找
本身只需少量信息，却先通过 data() 构造整批对象；历史较长时带来临时分配和回收。
图例对相同内容反复重建 DOM，内部缺口的折线则对全部画线段重新提交数据。
旧 Notebook 的 Base64 转换还保留不必要的普通数字数组中间副本。

这些开销主要发生在浏览器，须与服务端 RSS、容器统计及长期泄漏分别判断。
优化应减少无效复制和绘图写入，保持用户看到的数据、交互与错误行为。

## 方案对比

复用现有图表时间线维护查询索引，可消除热路径的全量 SDK 读取；索引随所属系列
提交和释放，不另建全局缓存或业务层索引。图例复用节点、分段复用数据与样式，
均可在已有职责内减少重复工作。

降低历史数量或刷新频率会改变业务；原地改写已发布行情／指标快照会破坏隔离。
重写指标算法、交易计算或裁剪存储结构的风险大于本轮已确认热点，不纳入本任务。
服务端强制 GC 与 Bun --smol 也不作为本次优化手段。

## 取舍结论

先消除整批查询与图例重建，再对缺口分段和 Base64 副本作局部等价优化；生产保留
一条正式链路。以相同输入的终态、真实 SDK 行为和三轮离线分配对照共同验收。
没有可验证收益的复杂方案不保留，累计分配下降不表述为常驻内存等比例下降。
