# 手动 ATR 风险下单面板

## 使用场景与设计初衷

用户在 market 看盘时，希望从按钮栏打开下单面板，以指定金额控制一次手动订单的
预计止损风险。使用 ATR 确定止损距离，按照交易所实际精度计算数量，并同时比较
做多和做空的参考结果。风险金额包含预计开仓和止损平仓手续费。

图表只提供初始品种和最小 K 线周期，面板可以修改品种、周期、ATR 根数和风险
参数。这不是自动交易策略：每次入场必须由用户点击，后续只完成该次成交核实、
保护单提交和结果查询；失败由用户处理，不自动再次交易。

已有项目具备 ATR／WSMA 的正式计算链、行情生命周期和共享图表，后端具有单笔
行情及交易接口。复用这些能力能避免新建另一套指标算法或把交易所规则散落到 UI。
既有看盘 API 只读取行情，交易使用独立且明确的 lwchart 写接口。ccxt-proxy2
已分别提供市场规则、账户费率和单笔交易路由，前端按这些实际契约对接。

手动看盘需要在多个品种间切换，并在图上直观看到参考开仓及保护距离。页面保留
已确认参数和草稿，窗口关闭不会丢失编辑。悬浮切品种时收起，平铺保留显示并切换
读取；仅更新身份，其他参数及编辑状态保持。平铺与设置浮层共存，便于边看边调。
悬浮与平铺共用面板，仅布局和宽度进入 URL。
两种形式可用空间不同，因此各自记住宽度；设置恢复默认、自选清空沿用草稿提交
流程，减少反复逐项编辑。示例标签缩短并放左侧，避免挤占右侧价格轴。
临时价格线由内聚的共享图表模块统一处理，market 只描述价格和显示状态；使用
原生价格线原位更新，无须维护历史线数据或将绘图细节散落到交易界面。

## 方案对比

持续订单管理系统可以处理长期恢复、自动补偿和保护单互斥，但会引入持久化任务、
后台追踪及更多自动写操作。本任务采用一次有时限的手动流程：入场确认后并发提交
两张保护单，再显示各自事实。手动核对可以读取订单，但不能隐含补发或撤单。

三张订单一起发送虽然接口调用少了等待，却无法确定保护数量及是否已形成仓位。
采用入场与成交核实串行、两张保护单并发，保留必要依赖。并发仅表示分别提交与
收集结果，不改变 ccxt-proxy2 现有账户请求门禁，也不承诺原子性。

余额和保证金的跨交易所预检成本较高。本任务直接提交通过价格／数量／风险容差
校验的入场请求，由交易所接受或拒绝；资金不足仍按明确错误展示。
报价差异由 lwchart 适配，有盘口时使用对应方向价格，否则用有效 last 作估算。

市价入场是首要交付。限价订单的长期等待和部分成交追加保护、现货库存与卖出
语义、反向合约换算不纳入首版；不通过静默转换交易所、品种或环境实现兼容。

## 取舍结论

首版覆盖 Binance／Kraken 线性永续的市价手动下单，并为其他来源保留面板入口。
ATR 留在既有浏览器计算链，价格网格与含费风险使用浏览器和 Bun 共用的纯计算
模块；Bun 执行短流程，ccxt-proxy2 继续承担单笔 Provider 适配。

不新增资金预检、自动写重试、自动平仓、自动补挂、OCO 或进程重启恢复。代价是
部分成交、保护失败及未知结果需要人工处理；结果必须分别说明成交与保护事实。
同品种旧仓继续由交易所按账户模式处理，本工具不提供独立仓位隔离保证。

后端市场规则明确区分已知、未知、不适用与无界；账户费率由独立路由提供，
Kraken 仅支持配置了费用查询凭据的实盘账户。订单模式只能从可空持仓字段获取
证据，不能依赖不存在的市场模式字段。

准入区分计算必需事实与交易所最终限制：报价、ATR、合约乘数、价格／数量网格、
账户费率和风险容差必须有效；未公开的上下限、名义金额校验依据及无法确认的
账户模式只提示，由交易所最终接受或拒绝。已知不支持的市场或双向模式仍禁用。
这样可使用实际路由完成手动交易，同时保留未知事实，不伪造规则或保证订单必然成功。
