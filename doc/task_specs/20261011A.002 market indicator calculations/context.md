# 库计算与末根更新

## 使用场景与设计初衷

已有 A–E、返回 C–G 时，正常业务只需要覆盖 E 并追加 F、G；C、D 只用于校验。
现有实现允许修正多根历史，并为 EMA 保存最近五根检查点，承担了不再需要的职责。
缺少 E 或历史不同属于防御性异常，应重新取完整 history_bars 并重新计算全部指标。

## 方案对比

保留自己的 EMA、只给其他指标接库，会形成两种播种规则和两条维护链路。
给库补历史状态恢复，也会继续承担正常场景不需要的回退能力。
使用原生 add／replace 并把历史异常交给完整重载，符合已经明确的业务边界。

只测试追加无法证明未闭合末根被多次替换时正确；以应用自己的计算器生成参考，
又无法发现适配层的共同错误。参考应直接新建原生库实例，从同一计算起点重放。

## 取舍结论

一次切换现有调用方并删除旧算法；使用元数据选择输入和结果角色，不写指标公式。
十一候选在本阶段逐项获得准入结论，仅开放合格计算；公开显示暂保留 EMA，等待副图与复合
输出接入。异常重载必须是真正重新请求与完整重算，不使用旧窗口补拼。

固定结果、常量窗口、首根替换及未定义后的恢复在替换生产计算前准入，不等到
显示阶段开放后再检查。8.3.0 是候选，合法 CCI NaN 用明确状态表示；状态缺陷不靠
请求同一数据或放宽精度解决。只有一根时新建原生实例仍是调用库，不维护库补丁。
完整行为遵守 [主任务 spec](<../20261011A unified technical indicators/spec.md>)；
参数与元数据继承 [前置 spec](<../20261011A.001 indicator metadata contracts/spec.md>)。
