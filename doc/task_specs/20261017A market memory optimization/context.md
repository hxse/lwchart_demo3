# 看盘内存优化

## 使用场景与设计初衷

用户通过 Cockpit 观察 lwchart-market 的内存，希望在业务行为等价的前提下降低占用。
容器只承担静态资源、鉴权及行情适配，图表、历史窗口和指标运行在浏览器中。
容器统计、进程驻留内存和 JavaScript 堆口径不同，必须分别测量，不能以监控读数
波动或 bundle 大小代替优化效果，也不能把浏览器收益宣称为容器收益。

## 方案对比

纯校验与绘图库解耦、校验借用输入、增量复用已有时间索引可以直接减少无效工作，
但必须保留输入校验、数据所有权和错误时的快照隔离。
指标结果在发布后保持不可变，未发布的批内更新可以复用自身存储；引入通用持久化
集合或改写指标算法成本更高，本任务不采用。

Bun --smol 可以改变垃圾回收频率，效果取决于请求负载；低占用时收益可能不明显，
不能只凭选项名称默认启用。缩减历史数量、降低刷新频率和隐藏窗口停更会改变既有
业务行为，不属于本任务。更换语言、容器基底或服务架构也不在范围内。

## 取舍结论

保留单份正式运行链路，以固定离线输入比较优化前后。采用职责清楚、可直接
消除分配且通过行为回归的修改，不将累计分配量下降误解为常驻内存等比例下降。
生产保持 Bun 默认 GC：小堆策略不能保证降低空闲 RSS，频繁回收还会增加延迟；
--smol 保留在显式诊断对照中，不增加用户运行配置。统计结果仅在当次回复报告，
可复用的测量程序随任务保存。
