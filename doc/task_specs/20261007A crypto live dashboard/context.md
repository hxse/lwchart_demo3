# 加密货币实时多周期看板

## 使用场景与设计初衷

项目已有 Svelte 5 与 Lightweight Charts 5 图表组件、网格布局和十字光标联动。
旧场景从 ZIP 内的配置与 CSV、Parquet 数据生成回测图表，支持浏览器查看以及通过
`src/lib-entry.ts` 导出 Notebook 使用的 `mountDashboard`。旧 `build:lib` 还承担构建后
复制文件的工作，其目的地需要改为 `~/dev/pyo3-quant/data/lwchart`。

新场景是加密货币手动看盘：打开页面就显示占满屏幕的四个周期，持续更新正在形成的
K 线；用户通过 URL 分享不同品种、周期、布局和 EMA 设置，也能展开右上角菜单调整。
本任务只做行情展示，不承接后续的账户订单、仓位或下单功能。

两种场景的数据生命周期不同。Notebook 图表使用已有文件快照，新看盘使用有鉴权的
CCXT HTTP 请求。因此入口、URL 解析、控制菜单和行情状态应隔离，图表渲染继续共享。

后端契约以 `http://127.0.0.1:5123/openapi.json` 为接口依据，配合 ccxt-proxy2 的
`src/router/auth_handler.py`、`src/router/trader_router.py` 和 `src/tools/ccxt_client.py`
理解执行语义：登录为 OAuth2 Password Grant，token 有效期 3600 秒，无 refresh token；
初始与增量行情分别使用 `/ccxt/fetch_ohlcv/latest-limit` 和 `since-limit`，返回
`rows` 与 `last_bar_completion_confirmed`，时间戳是 UTC 毫秒。

## 方案对比

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| 在旧 ZIP 看板中加入实时行情分支 | 可以直接使用旧页面外壳 | 文件加载、Notebook props、鉴权和轮询混在同一状态对象中，容易影响旧场景 |
| 新建页面与数据状态，复用原图表和网格 | 场景隔离，已有图表能力只有一份实现 | 需要为共享图表增加按系列增量更新接口，并将通用同步管理移到共享位置 |
| 引入另一套图表引擎或嵌入式 Widget | 可获得另一种成品外观 | 形成两套图表实现，已有组件不能直接复用，增加联动与维护成本 |

选择第二种方案。原 `LWChart` 当前在 `series` props 改变后删除并重建所有系列，
不能直接把每次 HTTP 响应重新交给该 props。应保留结构初始化链路，在同一控制器上
增加替换数据与追加／更新数据的接口，轮询使用既有系列的增量更新能力。

后端凭据只由宿主上的服务端适配层读取 TOML。开发期由 Vite 中间件提供相同的本地
HTTP 接口，构建后的独立运行服务使用 Bun；二者共用配置加载、鉴权和代理实现。
前端仅接收公开的显示默认值。直接把 TOML 密码注入浏览器构建，会让运行凭据进入
静态产物，也会把新场景与旧浏览器 settings 的本地存储绑定，故不采用。

## 取舍结论

- 使用同一份 Lightweight Charts 组件、系列控制器、图例和网格模板，不复制绘图系统。
- 用 Just 选择场景、构建配置和复制步骤；package.json 保留依赖与工具级原子命令。
- 默认是 Binance USDⓈ-M 的 `BTC/USDT:USDT`，可显式切换后端支持的其他 CCXT 身份。
- 初始每周期默认请求最多 1500 根，数量在 URL 和菜单中可控，最大 10000；不足时
  使用实际历史。后端倒数查询通过 `snapshot - (limit - 1) * interval` 推算起点，
  大量周线可能落到 Unix epoch 之前。
  周线因此用后端允许的 UTC 毫秒下界发起 `since-limit` 请求，不修改后端、不制造历史。
- 正常轮询与断网恢复均从已接受的实际末根时间戳含首请求 10 根；长断网用相同规则
  连续补页，不通过 `last + interval` 或本机时间猜测请求游标。
- EMA 保留正在形成的尾根之前的计算状态，每次更新重算尾根，避免同一根 K 线被
  重复递推。保留窗口滚动时不重新播种 EMA。
- 新界面把空间用于图表，控制菜单默认隐藏；错误提示保留在对应图表内，不假装数据
  一直实时可用。
